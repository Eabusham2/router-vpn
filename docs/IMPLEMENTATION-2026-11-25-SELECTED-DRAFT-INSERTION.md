# Selected earlier-hop measurements and unsaved draft insertion

The [later recursive continuation](IMPLEMENTATION-2026-11-25-RECURSIVE-SELECTED-CONTINUATION.md)
supersedes this record's single-private-intermediate restriction and its manual
desktop/Android continuation behavior. The original evidence below remains
attached to the source and case inventory that produced it.

This continuation implements the recursive editor interaction required by
[the reconciled product contract](REQUIREMENTS-RECONCILED.md). A measured candidate
can be inserted into the original unsaved draft after its temporary native owner
is fully DOWN. Named profile Save remains a separate action. Source, executable
fixture, hosted release, and installed-device evidence are recorded separately.

## Route qualification

The selected earlier-hop response family has an original paired WireGuard
entry, literal-address imported Shadowsocks 2022 intermediates, a paired
Shadowsocks 2022 final, and Start Layer Off on every member. Compare must have
actually selected Local. An original four- through 95-member source with no
private intermediate may measure through an eligible earlier imported stop.
Every operation captures the selected position, the complete original source,
the original trial and its positive selection epoch.

An earlier named proposal inserts the measured paired Shadowsocks member after
the measured stop, retaining every prefix and suffix member and the original
final. A penultimate named proposal preserves its existing behavior of replacing
the final. The candidate must be distinct from every original profile and
private proof identity, including identities in the unmeasured suffix.

The existing penultimate response family with zero or one original private
intermediate remains supported. Server-winning Compare trials do not publish
Local private-response offers or scores. This change does not grant these
Compare operations to AWG entries, hostname imports, enabled Start Layers, or
two-private-intermediate sources.

## Use in draft and named Save

The desktop draft picker exposes independent HTTP offers:

| Action | Captured offer | Result |
| --- | --- | --- |
| Use in draft | `draft_path`, `draft_action: insert-measured-hop` | Insert after the measured stop and preserve the entire suffix, including the original final. |
| Save a named profile | `proposed_path`, `proposal_action` | Save the separately compiled intermediate insertion or final replacement as a new complete profile. |

The two paths can differ at the penultimate stop. The desktop controller never derives
the draft insertion from the named final-replacement array. It compiles both
offers independently against their original sources, then recompiles and
revalidates the selected offer at adoption.

Use is available only from an original editor-draft operation. It carries no
profile name, writes no persistent connection profile, leaves Home selection
unchanged, and cannot start a normal connection. The desktop response binds the
original request, view, selected position and measurement; Compare also binds
its winning Local trial and selection epoch. It confirms the original native
DOWN and cleanup and returns the exact inserted path and public linked-profile
tokens to the owning editor revision. An ordinary Local operation has no
Compare selection epoch.

The original three-node selected response family can become a four-node draft.
The qualified all-imported selected family can similarly grow by one member up
to the 96-member source capacity. A selected source already containing a private
intermediate cannot use this operation to add a second one. Its independently
qualified named final-replacement offer remains available. A 96-member source
cannot insert a 97th member. Capacity checks are source and UI boundaries, not
evidence of a live 95-hop or 96-hop path.

The editor's subsequent measurement captures the edited draft anew, with its
new source, request and original native owner. On iOS the editor schedules the
next qualified position; Android and desktop offer the following Measure
action. It cannot reuse the consumed
candidate receipt. Each subsequent position still requires its own qualified
native path. Ordinary Local response drafts use the existing complete Local
compiler and original closed-prefix measurement owner. Existing routed-TCP
draft choices retain their original behavior and measurement meaning.

## Desktop and mobile integration

Windows, GTK and AppKit provide the separate draft action and preserve the
original final node. Their result callbacks reject a changed path, action,
source map, selected execution, epoch, or editor revision. Connected pickers
retain the named-profile workflow.

The macOS HTTP constructor now admits the corresponding bounded selected-draft
catalog, run, named Save, Use and Cancel requests, including deeper eligible
positions. Its checks still reject unknown fields, malformed scopes, positions,
tokens, duplicate nodes and paths inconsistent with the requested action.

The legacy connected response without an explicit source map is restricted to
its original three-node catalog shape. A larger selected route cannot obtain
that compatibility path merely by choosing the first imported hop.

Android and iOS retain their original compiled candidate proposals across native
DOWN. Draft adoption belongs to the captured editor transaction, preserves
the original suffix and final, and does not update Home or persistent profile
storage. An earlier insertion can reuse its matching compiled named proposal;
both clients freshly validate all linked sources before adopting it. Their
named Save/Load paths retain the execution choice and every unaffected member;
a penultimate named Save replaces the old final as specified above.

## Acceptance still requiring separate evidence

The authoritative Build-all run must package and publish the complete final
commit. An older green workflow or a partial run cannot certify these changes.
Client packages, ARM64 server images, checksums and generated production Compose
must all refer to that same commit.

Physical route and leak checks, network transitions, off-LAN interoperability,
device UI/DPI verification, private server integrations and live AI providers,
legitimate Apple provisioning, production deployment and ASUS household
fail-open acceptance still require their own observed evidence under
[the live release procedure](LIVE-RELEASE-EVIDENCE.md). Source and fixture results
do not substitute for those requirements.
