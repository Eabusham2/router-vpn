# Retained Unix Naive H2: source and acceptance boundaries

Prepared November 16, 2026 UTC. This unit implements the single paired Router
Naive H2 path in the existing retained Linux/macOS host. It does not establish
complete mode parity, a green release, physical-device acceptance or deployment.
The binding product scope remains
[REQUIREMENTS-RECONCILED.md](REQUIREMENTS-RECONCILED.md).

## Shipping path

Linux dispatches exact `naive-h2` through the existing owned controller instead
of the legacy connection fallback. The shared retained Unix physical-graph
predicate accepts the already-compiled H2 graph, and both Darwin PF state
parsers retain its exact mode through capture, readback and Off cleanup.

The shared Node compiler and retained native engine continue to own the
original source, node identity, credentials, private trust, selected DNS,
protection, effective MTU and restoration. Off, AES-256-GCM and
AES-256-GCM plus XOR whitening remain separate captured Start Layer choices.
Plain H2 uses its TCP lower; application UDP, including selected Home DNS and
the private MTU benchmark, travels through authenticated UoT-v2 over H2.
Resolver bootstrap remains separately captured by the existing policy.

This change does not admit Naive H3, REALITY, PQ REALITY, XHTTP or other
unproved retained Unix families. It leaves the existing Windows admission
and broader runtime implementation unchanged. Missing controllers, cancelled
captures and malformed policies still refuse before stopping a replacement
connection.

## Required native release acceptance

The new reusable [native workflow](../.github/workflows/unix-naive-h2-host.yml)
is a required dependency of the existing release aggregate. It consumes the
same run's exact-source runtime bundle on Linux AMD64/ARM64 and macOS
Intel/Apple Silicon. No caller input can select a historical source, narrower
case set or substitute workflow. The central artifact audit requires this job
alongside all pre-existing release dependencies, including installed Linux
SOCKS and imported-Shadowsocks execution.

| Boundary | Required execution |
|---|---|
| Linux retained host | 48 cases through the real installed controller, native engine, namespace, TUN and firewall |
| macOS retained host | 36 cases through the real installed controller, sealed native bundle, PF and utun |
| Authentication | Final username/password, trusted certificate, SNI, independently captured outer key and whitening refusals |
| Selected path | Authenticated original-node proof and selected Home DNS, including wrong-node and resolver failures |
| Lifecycle | Original protection, sealed temporary restoration, owned process and policy retirement |
| MTU | Actual original-path UoT datagrams, effective readback, retained Auto/Retest/Cancel and rollback behavior |
| Source and packaging | Current commit, complete runtime receipt, original image hashes, compiled case inventory, unchanged source before and after execution |

The original Linux case inventory and original 69-case macOS phase remain
required and unchanged. The new 48/36 cases execute in a separate bounded
phase; no existing operation or per-case deadline was enlarged. Each target
must emit all original case receipts, and the phase rejects missing,
duplicate, foreign, failed, skipped or raced results. A receipt is written only
after its owned workspace is retired.

The additional Linux component invokes the actual pinned Naive inbound and
Cronet outbound for all three Start Layers, with private node proof, selected
DNS, benchmark hold/release and source cancellation. Its kernel/TUN boundary
is explicitly modeled. The macOS phase uses the installed static native
composition; it does not claim dynamic-library evidence from a Linux fixture.

## Evidence still required

All four new hosted native phases, exact-current publication, real-device
network transitions/leaks/visual checks and private deployment remain pending.
The new gate cannot be considered passed from its source inventory or the
successful local compile alone.

Other retained Unix mode families remain open requirements. Protected dynamic
Direct Tor on Windows/macOS also remains open: the existing non-Linux import
policy and native guardian capability reject that combination. Existing
literal obfs4 protection and captured predecessor paths must be preserved;
this is not a claim that all Tor support is absent. See
`cmd/client/tor_bridge_capabilities.go`, `cmd/client/tor_bridge_import.go` and
`internal/mobiletor/desktop_physical_policy.go` for those distinct boundaries.
