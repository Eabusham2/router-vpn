# SOCKS mobile execution and retained MTU restoration

This increment connects the schema-3 SOCKS Server/Compare preparation and native
Box owner to the actual mobile CommandServer. The four separate public functions
are `NewRouterNodeChainSOCKSExecution`,
`NewRouterNodeChainSOCKSExecutionLaunch`,
`RouterNodeChainSOCKSExecutionFromLast`, and
`RouterNodeChainSOCKSExecutionNewCommandServer`. The launch kind is
`routervpn-node-chain-socks-execution-preparation-input`.

The factory retains the original plan, preparation, SOCKS source, caller-local
outbound registry, native association capture, CommandServer and StartedService.
Bind and every later native observation require those original owners. Another
server, equal-content preparation, copied plan or capture, retired owner, and the
separate Local SOCKS factory cannot borrow that authority. Capture cleanup joins
the retained original close even after cancellation; it does not replace the
independent native Instance close receipt.

The typed retained mobile capsule can be created only after both the original
shared execution and its actual native reader have joined retirement. It retains
the original source and policy pointers, observed reader nonce and generation,
target, interface, and MTU. The resulting preparation changes only the TUN MTU
to that original observation. The original source identity, selected execution,
same-endpoint comparison, credentials and ordered prefix envelope remain intact.
Fresh authenticated discovery is mandatory before adoption, and the selected
path must prove itself again without repeating Compare or querying the retired
reader. Ordinary JSON replay cannot recreate the private MTU authority.

The separate canonical launch parser preserves a saved Last record and its
selected Local or Server result. A saved record grants no live readiness. Missing
Last data, a schema downgrade, changed configuration identity, duplicate JSON
members, noncanonical bytes, or the generic launch kind are rejected.

## Remaining acceptance

This shared bridge does not itself establish an Android or Apple device result,
an installed system TUN, kernel protection, or encrypted physical packet-entry
acceptance. The separate hosted encrypted SOCKS server suffix and native client
association gates remain required. Android host integration is a dependent
increment. Apple host/UI and desktop physical execution adapters still require
their own typed adoption and acceptance. The supported SOCKS Server/Compare
topology remains the exact three-member path. This is not completion of the
full historical requirements.
