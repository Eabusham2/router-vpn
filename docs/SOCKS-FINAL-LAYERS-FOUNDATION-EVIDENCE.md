# Captured SOCKS final-layer foundation

This additive source unit permits an independently captured Off, AES-256-GCM,
or AES-256-GCM plus XOR-whitening final in the exact three-member typed SOCKS
Server suffix. It preserves SS2022 credentials, the original negotiated SOCKS
TCP-control/UDP-association owner, exactly two native outbounds, no CONNECT UoT
on either suffix outbound, original source seals and leases, and joined cleanup.
Generic and CONNECT constructors remain closed to the SOCKS source.

The public desktop predicate and all native editors still require final Off.
This foundation does not establish public Server/Compare, installed kernel, or
full entry-to-final encrypted acceptance for the added final layers. Follow-up
public/backend and editor admission must retain that distinction and require
the hosted native evidence before claiming support.

## Mandatory acceptance

The existing authoritative release invokes `desktop-native-runtime.yml` for all
six native targets. Its ordinary build step now requires the final-layer runner.
The existing matching-host Linux block in `build-native-runtime.py` retains the
original SOCKS Server invocation and appends the new runner and native gate on
both Linux architectures. The original `TestOriginalSOCKS` ownership phase also
remains unchanged. The two new Python files and the consumed native workflow
are included in the exact runtime source fingerprint.

The new gate requires all 18 shared source verdicts, all 12 encrypted suffix
verdicts, and an actual counterfactual restoring the native Off-only guard. The
counterfactual must fail the exact whitening leaf at its original capture
witness; success, unrelated failures, duplicates, omissions, race reports and
foreign records are rejected. Every package retains a 120-second Go test limit
and 600-second outer compile/test limit. Three mandatory serial phases therefore
have an 1,800-second maximum; their caller has 1,900 seconds including finite
orchestration overhead. Existing stage and workflow job limits are unchanged;
this arithmetic concerns the new caller only, not the maximum of the full job.

The encrypted identity-negative case witnesses a wrong-identity response from
the actual final service. It is not a shipping Connected-proof-consumer verdict.
Other cases require changed key/whitening/route/token/DNS/cancellation responses
and retained association cleanup from the original encrypted provider.
